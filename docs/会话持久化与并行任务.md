# 会话持久化、异步对话、并行任务与工程工作区

本文记录 /harness 自研对话页的四项能力：**会话可恢复 + 工程长期记忆**、**可断线续跑的异步对话任务**、**检测项并行评定任务中心**，以及**围绕当前检测工程的产物工作区**。目标是让对话能接着上文继续做报告，让长回合在后台继续执行、可切走、可排队/取消，把批量评定从“逐项点、逐项等”改为可观察的并行任务，并让右侧工作区只呈现当前工程真正相关的文件。

## 1. 会话持久化

### 1.1 存储位置

| 内容 | 路径 | 说明 |
|------|------|------|
| 会话 transcript | `data/chat_transcripts/<sessionId>.json` | 消息、工具轨迹、计划、摘要、轮次 |
| 工程长期记忆 | `data/chat_memory/<sha1(project)[:16]>.json` | 按工程名隔离的事实、摘要、报告 |
| 会话元数据 | `data/chat_sessions.json` | 标题、工程、隐藏标记等轻量元数据 |

实现：`webapp/backend/chat_store.py`。

- 所有写入使用 `RLock` + 临时文件 + `os.replace` 原子替换，避免半截 JSON。
- transcript 字段：`messages / tools / plan / summary / promptCount / updatedAt`。
- 每个用户轮次结束后调用 `record_turn_memory`，把本轮问题/回答摘要和工程事实写入长期记忆；事实最多 30 条、摘要最多 12 条。
- `extract_report_paths` 从回答与工具结果中识别 `report_generator/exports/*.docx` 和报告预览/下载链接，写入“最近报告”。

### 1.2 自动恢复

- 前端连接 `/api/chat/ws?resume=1`。
- 后端 `latest_session(project)` 按当前工程找最近会话，并额外检查**本地 transcript 是否有消息**；旧会话没有 transcript 时返回空，避免恢复出空白页。
- 恢复成功后 `ready/resumed` 帧携带 `history`（最近 300 条消息、120 条工具、50 条计划）和 `memoryCount`。
- 浏览器端 `loadTranscript` 优先使用后端 history，后端没有时才回退 `localStorage`。
- 切换工程或新建会话时，旧会话不会被删除；侧栏“最近会话”可手动切换。

### 1.3 长期记忆注入

新会话第一轮（`promptCount == 0`）才注入，恢复会话不重复注入：

```text
【工程长期记忆 · 系统自动注入，不是用户发言】
...工程快照、最近报告、最近工作...
【用户当前请求】
<用户原文>
```

- 注入块上限约 2800 字，避免挤占模型上下文。
- 快照包含：已勾选、已录入、已评定、数据行数。
- 前端侧栏“记忆 N”打开弹窗，展示同一份 `GET /api/chat/memory` 数据。

### 1.4 面向“继续上文报告”

- 最近报告路径会进入长期记忆；新一轮可直接说“把刚才那份报告重新生成/改结论”，模型能从注入块看到路径。
- 会话消息和工具轨迹都在 transcript 中，刷新页面、重启后端后可恢复。
- 注意：长期记忆是**工程级**的，不区分操作人；当前部署按单机单用户设计。

### 1.5 单会话写句柄与多标签接管

DSH ACP 对同一个 session 只允许一个写句柄。浏览器刷新或多标签会各自拉起一个 ACP 进程，旧进程不退出就会占着会话，表现为“恢复会话失败：Internal error”。

`webapp/backend/routers/chat.py` 的处理：

- 后端在内存中维护 `_SESSION_OWNERS`，记录每个 session 当前由哪个 `AcpClient` 持有；
- 自动恢复和手动切换都走 `_resume_session`；遇到 "active write handle" 错误时，先关闭本后端内的旧 `AcpClient`，等 0.25 秒后重试一次；
- 接管时向旧页面发送“会话已被另一个窗口接管，请刷新页面”并关闭其 WebSocket，避免旧页面显示已连接却无法发送；
- 手动切换会话不再关掉当前会话：每个会话保留独立 runtime，切走只解除订阅，原回合继续在后台执行；切回时重新订阅并续显。目标会话恢复失败时当前对话仍可用；
- `AcpError` 保留 JSON-RPC 的 `code/data`，锁冲突会转成明确提示，而不是只显示 Internal error；
- 关闭 WebSocket 时释放该客户端持有的会话登记。

限制：接管只针对**本后端进程内**的旧 ACP 进程；如果后端被强杀后留下孤儿 ACP 进程，重启后可能需要手动结束这些进程。

## 2. 异步对话任务

### 2.1 常驻运行时与连接

对话任务不再绑定某一次 WebSocket 连接。后端为每个 DSH 会话维护一个常驻的 `ChatSessionRuntime`，浏览器连接只是它的一个订阅者：

- 第一次发送消息时创建 runtime，持有 ACP 客户端、transcript、队列、当前任务和待确认权限；
- 页面刷新、关闭标签、网络抖动只触发 `detach`，**不会取消正在执行的回合**；
- 重新连接时带上 `session=<sessionId>` 即重新订阅同一 runtime，`ready/resumed` 返回当前快照；
- 同一会话严格串行：当前任务未结束时新消息进入队列；不同会话是不同 runtime，可以各自执行，受本机 DSH/模型并发能力约束；
- 页面上切换会话只 `detach` 当前 runtime，不取消当前回合；目标会话已有 runtime 就直接 attach，没有才新建 ACP。因此 A 执行中可以切到 B，A 继续跑，B 也能独立发送；同一页面一次只订阅一个会话。
- 没有订阅者且没有排队/执行中的任务时，runtime 空闲 120 秒后关闭 ACP 进程；transcript 和长期记忆保留，下次打开再恢复；
- 后端进程重启**不能**续跑正在生成的回合：`data/chat_jobs.json` 中 queued/running 的任务会标记为 `interrupted`（“后端重启，对话任务已中断”），已流式写入 transcript 的文本仍保留。

### 2.2 队列与取消

- 当前任务执行中继续发送，后端创建 `status=queued` 的任务并立即回 `queued` 帧；队列 FIFO，单会话最多 20 条，超出返回“排队任务过多（最多 20 条）”。
- 前端顶栏显示“后台执行中”或“后台执行 · 待执行 N”，输入框保持可用，底部提示“可继续发送”。
- “停止全部”/单任务停止：
  - 排队中的任务立即移除，并在对话中补一条 assistant“已取消”；
  - 正在执行的任务向 DSH 发 `session/cancel`，保留已生成文本；若一个字都没生成，补一条“已停止”；
  - `queue` 帧同时携带 `busy`，避免停止当前任务时前端提前显示“已连接”。
- 队列清空、取消、完成都会广播 `queue`；排队项取消额外广播 `cancel_notice`，因此多个订阅窗口看到一致结果。
- 左侧“最近会话”行用绿色运行点显示 `busy`，`queue>0` 时提示“待执行 N”。切到其他会话后，后台会话开始/完成/取消仍通过全局 `sessions` 帧刷新运行点，不要求停留在该会话。
- 权限确认请求保存在 runtime 内存中（等待 300 秒）；页面断线重连后会重放未处理的 `permission_request`。

### 2.3 断线与重连

- 前端 WebSocket 地址为 `/api/chat/ws?resume=1&session=<id>`；没有 `session` 时按当前工程自动恢复最近一个有本地 transcript 的会话。
- 非主动关闭（网络断开、页面刷新）后 1.5 秒自动重连；接管、主动登出等场景不重连。
- `ready/resumed` 快照包含 `history{messages,tools,plan,title}`、`busy`、`queue`、`assistantId`、`memoryCount`；前端按消息 id 合并，继续把后续 chunk 追加到同一个 assistant 气泡。
- 实测：任务执行中刷新页面，4 秒后仍显示“后台执行 · 待执行 1”，最终自动回到“已连接”，断线期间及之后的回答都写入 transcript。
- 重连只恢复“显示与订阅”，不会重新发送 prompt；因此不会因刷新重复执行同一任务。
- 会话切换同样只是重新订阅：切回正在执行的会话时，`busy/queue/assistantId` 让前端继续追加同一个回答气泡，不会从头再答。

### 2.4 API 与前端入口

| 接口 | 说明 |
|------|------|
| `GET /api/chat/jobs?limit=12` | 最近对话任务，limit 1..50；runtime 仍存在时补 `live=true`、实时 `queue`，当前任务状态覆盖为 running |
| `POST /api/chat/jobs/{job_id}/cancel` | 停止一个任务：排队项立即取消，执行项发 `session/cancel`；任务不存在返回 404 |
| `GET /api/chat/memory` | 当前工程长期记忆，见 1.3 |
| `WS /api/chat/ws?resume=1&session=<id>` | 对话与任务事件流 |

任务记录写在 `data/chat_jobs.json`，最多保留 80 条；字段包括 `id/session_id/project/title/prompt/status/message/assistant/queue/pid/created_at/started_at/finished_at`。状态为 `queued/running/done/failed/cancelled/interrupted`。

WebSocket 任务相关帧：

- `queued`：`{jobId, queue}`，消息已入队；
- `queue`：`{queue, busy?, cancelled?}`，队列变化；
- `prompt_start`：`{jobId, queue}`，开始执行当前任务；
- `cancel_notice`：`{jobId, messageId, text}`，某个排队任务被取消；
- `sessions`：`{items:[{sessionId,title,project,updatedAt,busy,queue}]}`，全局会话列表；任意会话开始/结束/取消都会刷新；
- `prompt_end`：`{jobId, stopReason, queue, memoryCount}`，当前任务结束；
- `error`：带 `jobId` 表示任务失败，前端标记当前回答；不带 `jobId` 的是操作错误，不误伤流式回答；
- `closed`：ACP 进程结束或被接管。

前端入口：

- 对话顶栏：连接状态、后台执行/待执行数、“停止全部”；
- 输入框：执行中仍可发送，自动排队；
- 左侧“最近会话”：每行显示运行点；执行中可切走，原会话继续后台执行，切回后恢复流式/完成状态；
- “自动化任务”面板的“对话任务”区：1.5 秒轮询任务，显示状态/时间/队列，可停止单条。

### 2.5 与并行评定任务的区别

- **对话任务**：一次 DSH 智能体回合，按会话串行；取消走 ACP `session/cancel`；结果写入 transcript。
- **并行评定任务**：一次批量评定，把多个检测项分给线程池并发计算；同一时间只允许一个评定任务；全部完成后一次性写回 `ProjectState`，取消是协作式的。
- 两者都出现在“自动化任务”面板，但数据分别存 `data/chat_jobs.json` 与 `data/tasks.json`，互不阻塞。

### 2.6 限制

- 异步只跨浏览器连接，不跨后端重启；重启后运行中的对话标记为 interrupted，需要重新发起。
- 同一 DSH 会话仍只有一个写句柄；多窗口同时打开会触发接管提示，这是为了避免两个页面同时写同一会话。
- 每个后台会话各自持有一个 ACP 进程；切换会话/切回可能新建进程，空闲 120 秒后才回收。并发数受本机 DSH/模型能力限制，不是无限并行。
- 队列按会话隔离，上限 20；任务记录最多保留 80 条。
- 所有状态存本机 JSON，不做多机同步。

## 3. 并行任务中心

### 3.1 为什么不是边算边写

评定结果最终要写回共享的 `ProjectState`。如果多个线程直接写 `assessment_results`，会出现：

- 某检测项读到别的项写了一半的状态；
- 自动保存与评定写回互相覆盖；
- 报告生成读到不完整结果。

因此采用**快照隔离 + 单点写回**：

1. 启动时在 `state._lock` 内复制已勾选检测项的列定义、行数据、评定输入/选项；
2. 各 worker 只读自己的快照，调用纯评定函数 `assess(...)`；
3. 全部结束后，协调线程一次性写回 `assessment_results / options / inputs`；
4. 写回前后校验工程名，用户切走工程则不写回。

实现：`webapp/backend/task_runner.py`。

### 3.2 任务模型

```json
{
  "id": "task-20261117122241-e84030",
  "kind": "assessment_parallel",
  "title": "并行评定已勾选检测项",
  "project": "工程名",
  "status": "running|done|partial|failed|cancelled|interrupted",
  "total": 4,
  "completed": 4,
  "failed": 0,
  "cancelled": 0,
  "workers": 4,
  "items": [
    {
      "key": "钻芯法检测（梁）",
      "base": "钻芯法检测",
      "component": "梁",
      "status": "queued|running|done|failed|cancelled|interrupted",
      "duration_ms": 13,
      "message": "结论或错误",
      "result": {"ok": true, "conclusion": "...", "errors": [], "warnings": []}
    }
  ]
}
```

- 任务列表持久化到 `data/tasks.json`，最多保留 30 条。
- 后端重启时，上次 `running/queued` 的任务和条目改为 `interrupted`，不会假装还在跑。
- 同一时间只允许一个并行任务；避免两个任务同时写回同一工程。

### 3.3 并发与取消

- 并发度：`STRUCTURAL_TASK_WORKERS`，默认 4，范围 1..8；实际 worker 数取 `min(并发度, 检测项数)`。
- 线程池：`ThreadPoolExecutor(max_workers=workers, thread_name_prefix="assess")`。
- 当前评定是纯 Python 计算，受 GIL 限制；并发收益主要来自 I/O 和避免逐项串行等待。更大的工程可把 worker 换成进程池或 ACP worker，接口不变。
- 取消是协作式的：设置 `cancel_requested` 后，**已开始的项跑完**，未开始的项标记 `cancelled`，不会强杀线程。
- 取消后已完成的项仍会写回，避免白算。

### 3.4 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/tasks?limit=12` | 最近任务列表 |
| GET | `/api/tasks/{id}` | 任务详情 |
| POST | `/api/tasks/assess` | 启动并行评定，body：`{"sheet_keys": [], "title": ""}`；空数组表示全部已勾选项 |
| POST | `/api/tasks/{id}/cancel` | 请求停止 |

错误约定：

- 已有任务在跑：`409`，message “已有并行任务在运行，请等待完成或先停止”；
- 没有可执行检测项：任务创建后立即 `failed`，message “没有可执行的检测项”。

路由：`webapp/backend/routers/tasks.py`，在 `webapp/backend/main.py` 注册。

### 3.5 前端入口

`webapp/frontend/src/views/ChatView.vue`：

- 左侧“自动化任务”打开右侧面板，展示当前工程勾选/录入/评定进度；
- “并行评定已勾选项”启动任务；
- 卡片展示任务状态、完成数、失败数、worker 数、逐项状态与失败原因；
- 运行中可点“停止（已开始的项会跑完）”；
- 面板每 1.5 秒轮询 `/api/tasks`，关闭面板或离开页面停止轮询。

## 4. 工程工作区

/harness 右侧“工作区”不是源码文件浏览器。DSH 的 Files 以 Session cwd 为根；本产品的 cwd 是自身源码，直接照搬会把 cad_agent/、deepseek-harness/、docs/ 等目录暴露给检测人员。这里把**当前检测工程**当作语义根，做一份只读虚拟清单，不新建每工程物理目录，也不迁移历史产物。

### 4.1 展示内容

| 分组 | 来源 | 说明 |
|------|------|------|
| 检测报告 | 记录库 report_records，按当前工程名过滤 | 显示报告编号、结果表项数、模板、生成时间、大小 |
| 原始记录 | 记录库 original_records，按当前工程名过滤 | 显示行数、模板/工作表、生成时间 |
| 上传附件 | data/uploads/，按修改时间倒序 | 没有工程字段，统一标“本机上传”，不冒充属于当前工程 |
| 工程快照 | ProjectState.filepath 与 autosave_path 去重 | 显示文件名与保存时间；JSON 可文本预览 |

- 顶部工程摘要卡复用当前工程状态：已勾选、已录入、已评定、数据行数、快照名/时间。
- 记录库中的历史记录可能指向已删除文件。接口默认 include_missing=false，只返回文件仍存在的条目；返回 missing/missing_total，前端提示“已隐藏 N 条文件已缺失的历史记录，记录库仍保留”。需要排查时可传 include_missing=true。
- counts 只统计文件仍存在的条目，避免出现“计数 16、列表只有 2 条”的错觉。

### 4.2 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/workspace/overview?q=&limit=60&include_missing=false | 当前工程工作区总览；q 同时搜报告/原始记录；limit 限制每类条数（1..200） |
| GET | /api/workspace/download?path= | 下载项目根内的文件，响应为附件 |
| GET | /api/workspace/file?path= | 文本/图片/binary 预览；文本上限 200KB |
| POST | /api/workspace/upload | {name, data}，data 为 dataURL；保存到 data/uploads/YYYYmmdd_HHMMSS_<安全文件名> |
| GET | /api/workspace/tree?path= | 旧源码文件树，仅保留兼容；前端默认不再调用 |

返回骨架：

```json
{
  "project": {"name": "...", "checked_count": 4, "filled_count": 4, "assessed_count": 4, "total_rows": 129, "snapshot_name": "autosave.json", "snapshot_at": 1763358000},
  "counts": {"reports": 2, "originals": 11, "uploads": 6, "snapshots": 1},
  "total": 20,
  "missing": {"reports": 14, "originals": 0},
  "missing_total": 14,
  "sections": [{"key": "reports", "title": "检测报告", "items": [], "total": 2}]
}
```

条目字段：id/kind/name/path/filepath/size/at/exists/preview/downloadable/meta/detail/where。preview 为 docx|pdf|image|text|none；where 用于区分同名报告/原始记录的父目录。

### 4.3 前端交互

- 左侧“工作区”打开右侧面板；宽屏（≥1100px）默认展开。
- 搜索框 250ms 防抖；过滤 chips：全部 / 报告 / 原始记录 / 附件 / 快照，带数量。
- 点击条目：docx 打开预览弹窗（/api/report/preview，首次调用本机 Word 转 PDF，之后用缓存）；图片/PDF 用 /api/workspace/file；文本直接显示前 16000 字；其它格式提示下载。
- 详情卡提供“在线预览 / 下载 / 定位”（定位调用 /api/report/reveal 在资源管理器中选中文件）。
- 底部“上传附件”仍走 /api/workspace/upload；上传成功后刷新工作区并切到“附件”。
- 插件管理、自动化任务与工作区共用右侧 aside，三个面板互斥，关闭时清理预览与轮询。

### 4.4 与 DSH Files 的差异与限制

- DSH Files 按 Session cwd 逐层列目录；本工作区按工程语义聚合记录库与工程文件，**不遍历源码目录**。
- 虚拟清单是只读视图，不改变历史记录的磁盘位置；删除记录不会删除文件，删除文件也不会删除记录（只会在默认视图中隐藏）。
- 上传附件没有工程归属字段，只能标“本机上传”。
- docx 预览依赖本机 Word；未安装 Word 时只能下载。
- 窄屏（约 500px）下 docx 预览弹窗中的 PDF 页面会被裁切，桌面端不受影响。

## 5. 验证记录

- 会话：发送“只回复两个汉字：好的”得到“好的”；刷新后自动恢复同一会话，消息 2 条；`memoryCount=1`。
- 记忆：弹窗显示已勾选 4 / 已录入 4 / 已评定 4 / 数据 129 行、最近报告 3 个。
- 并行：4 个已勾选检测项，workers=4，全部 done；单项耗时约 6–10ms；任务 ID 示例 `task-20261117122241-e84030`。
- 后端重启后，上次运行中的评定任务会标记 `interrupted`；对话任务同样标记 interrupted，但已流式写入 transcript 的文本保留。
- 异步对话：发送长问题后 2 秒显示“后台执行中”，再发一条显示“后台执行 · 待执行 1”；执行中刷新页面，4 秒后仍为后台执行，最终自动回到“已连接”并补齐两条回答；点“停止全部”后当前项显示“已停止”、排队项显示“已取消”，对应任务状态为 cancelled。
- 跨会话并行：A 发送长问题后切到 B，B 顶部为“已连接”，A 行显示绿色“后台执行中”运行点，A 仍在生成；1 秒后 resume B 成功且 A `busy=true`；切回 A 仍为 `busy=true`；A 执行中新建 C 成功，A 继续运行并继续收到 20 个 chunk。UI 复测中运行点在发送后 0.5 秒内出现；在 B 页面取消 A 后 2 秒内运行点消失，A 的历史行保持可见。
- 多标签接管：两个连接同时自动恢复同一会话，第二个连接接管成功，第一个连接收到“会话已被另一个窗口接管，请刷新页面”；刷新后恢复同一会话，未再出现 Internal error。
- 工作区：当前工程默认返回 20 条（报告 2 / 原始记录 11 / 附件 6 / 快照 1），隐藏 14 条文件已缺失的报告记录；include_missing=1 时报告恢复为 16 条。搜索“钻芯”命中 3 条；过滤“报告”后 2 条；docx 在线预览 25 页正常；1440×900 与 500×900 均无页面横向溢出。

## 6. 已知限制

- 线程并发受 GIL 限制，CPU 密集型评定不会线性加速；
- 任务进度是“已完成项数”，不是单构件百分比；
- 一个任务内某检测项失败不会阻止其它项；最终状态为 `partial`；
- 任务历史保留 30 条，超过后自动丢弃最旧记录；
- 长期记忆按工程名隔离，同名工程会共享记忆；
- 并行任务只覆盖评定，不含报告生成；报告生成仍需在结果写回后串行执行；
- 异步对话只跨浏览器连接，不跨后端重启；重启后 queued/running 任务标记 interrupted，需要重新发起；
- 同一 DSH 会话仍只有一个写句柄，同一会话的对话任务严格串行；队列上限 20，任务记录最多保留 80 条；多窗口同时打开会触发接管提示；
- 不同会话可以并行，但每个会话一个 ACP 进程；实际并发受本机 DSH/模型能力限制，切换会话可能新建进程；
- 工作区是虚拟清单，没有“每工程独立目录”，也不会自动清理孤立文件；
- 工作区默认隐藏文件已缺失的记录，排查时需显式 include_missing=true；
- 500px 窄屏下 docx 预览弹窗的 PDF 内容会被裁切，桌面端不受影响。
